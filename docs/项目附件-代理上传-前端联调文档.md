# 项目附件：代理上传 —— 前端联调文档

> 适用后端版本：本轮「统一代理 + 双存储」改造后（对应 commit 见 git log）。
> 与前端协作的核心变化：**浏览器不再直传 OSS，文件字节一律先 PUT 到后端，由服务端写入当前存储策略（OSS / 本地磁盘）**。

---

## 1. 背景：为什么改

前端联调 `PUT /api/v1/projects/{pid}/attachments/{aid}` 返回 500，根因两层：

1. **后端此前根本没有这个上传端点**——`AttachmentController` 只有 POST 创建/确认、GET 下载/预览，没有 PUT 上传映射，请求落空。
2. `GlobalExceptionHandler` 的 `Exception.class` 兜底把 `NoResourceFoundException` 吞成 500「服务暂时不可用」，掩盖了「路径不存在」的真实原因。

本次改造后：

- 代理 PUT 成为**唯一上传入口**，字节经后端写入当前存储策略，**浏览器不再直传 OSS** → 绕开 OSS 跨域预检（CORS）问题；
- 未映射路径正确返回 **404**（不再 500）；仅 GET 的路径发 POST 返回 **405**；
- **本地回退模式（未启用 OSS）从不可用变为完整可用**：文件落本地磁盘，preview/content 可用。

---

## 2. 上传链路总览

```
前端                                     后端
 │  1) POST /projects/{pid}/attachments   │ 创建 PENDING 附件 + 签发代理上传凭证
 │  ────────────────────────────────────▶ │ 返回 { attachmentId, uploadUrl, method:PUT,
 │                                       │         expiresAt, headers }
 │                                       │
 │  2) PUT uploadUrl（原始字节）           │ 鉴权 + 幂等 → 写入存储策略（OSS/本地）
 │  ────────────────────────────────────▶ │ 响应 204 No Content
 │                                       │
 │  3) POST .../{aid}/confirm             │ 校验对象已存在 → 置 READY
 │  ────────────────────────────────────▶ │ 返回 { attachmentId, status:"READY" }
 │                                       │
 │  4) GET preview-url / preview / content│ 预览/展示/下载（原有流程不变）
```

**关键点**：步骤 2 的 `uploadUrl` 现在是**后端代理相对路径**，不再是 OSS 直传预签名地址；`method` 固定为 `PUT`。步骤 2、3 都需携带 `Authorization: Bearer` 与 `Idempotency-Key`（步骤 2 由 IdempotencyFilter 强制）。

---

## 3. 接口明细

### 3.1 创建凭证 `POST /api/v1/projects/{projectId}/attachments`

请求体：

```json
{
  "fileName": "design.png",
  "contentType": "image/png",
  "sizeBytes": 20480
}
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `fileName` | 是 | 原始文件名，≤512 |
| `contentType` | 否 | MIME，≤255 |
| `sizeBytes` | 是 | 文件大小（字节），**必须 >0**；超过上限（默认 50MB）返回 413 |

响应（HTTP 201）：

```json
{
  "data": {
    "attachmentId": "0197a2d4-…",
    "uploadUrl": "/api/v1/projects/{pid}/attachments/{attachmentId}",
    "method": "PUT",
    "expiresAt": "2026-08-21T14:00:00",
    "headers": { "Content-Type": "image/png" }
  },
  "requestId": "req-…"
}
```

- `uploadUrl` 为**相对路径**，`method` 固定 `PUT`，`headers` 携带应回传的 Content-Type（凭证声明了 `contentType` 时非空，否则为空对象）。
- `expiresAt` 为凭证过期时间（UTC，默认 900 秒）；过期后上传会被业务侧拒绝，前端应重新走 3.1。

### 3.2 代理上传 `PUT {uploadUrl}`（相对路径解析见 §4.1）

| 项 | 值 |
|---|---|
| 方法/路径 | `PUT /api/v1/projects/{projectId}/attachments/{attachmentId}` |
| 请求头 | 浏览器 Cookie 自动携带；`X-XSRF-TOKEN`（写请求必填）<br>`Idempotency-Key: <uuid>`（**必填**，缺失返回 400）<br>`Content-Type`（可空，建议按 3.1 凭证 `headers` 回传） |
| 请求体 | **原始文件字节**（不要包 JSON，不要 base64） |
| 成功响应 | **204 No Content**（无响应体） |

业务校验（服务端）：

- 非项目成员 → `403 FORBIDDEN`；
- 附件不存在/不属于该项目 → `404 ATTACHMENT_NOT_FOUND`；
- 附件状态非 `PENDING`（重复上传/已确认）→ `409 ATTACHMENT_NOT_PENDING`；
- 字节数超 `sizeBytes` 声明上限 → `413 ATTACHMENT_TOO_LARGE`。

### 3.3 确认 `POST /api/v1/projects/{projectId}/attachments/{attachmentId}/confirm`

- 服务端校验对象**已真实存在于存储**（OSS `doesObjectExist` / 本地文件存在），否则 `409 ATTACHMENT_NOT_UPLOADED`；
- 校验通过置 `READY`，返回：

```json
{ "data": { "attachmentId": "0197a2d4-…", "status": "READY" }, "requestId": "req-…" }
```

> 上传后**必须**调用 confirm；只有状态为 `READY` 的附件才能被 preview-url / preview / content 访问（否则 `409 ATTACHMENT_NOT_READY`）。

### 3.4 展示 / 下载（原有流程不变）

| 接口 | 用途 |
|---|---|
| `GET .../attachments/{aid}/preview-url` | 返回预览类型 + 不含凭证的相对 `previewUrl` + 预签名 `downloadUrl`（本地模式下 `downloadUrl` 为 `null`，用 preview/content 代替） |
| `GET .../attachments/{aid}/preview` | 内联内容代理，使用 HttpOnly Cookie 鉴权、HTTP Range 分段、`?raw=1`；URL 不含 Token |
| `GET .../attachments/{aid}/content` | 鉴权下载代理，`content.url` 的稳定展示地址（项目内长期有效） |
| `GET .../attachments/{aid}/download-url` | 预签名下载地址（**OSS 模式**可用；本地模式返回 `501 ATTACHMENT_DOWNLOAD_UNSUPPORTED`） |

## 4. 前端实施要点

### 4.1 `uploadUrl` 是相对路径，必须拼 API base origin

改造后 `uploadUrl` 不再是可直连的绝对地址。上传前需解析为绝对地址，与前端现有 `resolvePreviewUrl` 同法：

```ts
const absoluteUploadUrl = new URL(uploadUrl, apiBaseOrigin).toString();
```

其中 `apiBaseOrigin` 为后端 API 的 base origin（如 `https://api.example.com`，不含 `/api/v1`）。**不要**把它当作当前页面 origin 的相对路径去 fetch，否则会打到前端域名的 `/api/...`。

> 注意：若前端有 vite proxy 把 `/api` 重写为 `/api/v1`，`new URL(url, origin)` 得到的是 `/api/v1/...`，此时直接用即可（不要再叠一次 `/api/v1`）。

### 4.2 上传必须带的三个东西

```ts
await fetch(absoluteUploadUrl, {
  method: 'PUT',
  credentials: 'include',
  headers: {
    'X-XSRF-TOKEN': csrfToken,
    'Idempotency-Key': crypto.randomUUID(),
    ...credential.headers,          // 凭证返回的 Content-Type（若有）
  },
  body: file,                        // 原始 File/Blob，不要包 JSON
});
```

- **`Idempotency-Key` 缺失会直接 400** `IDEMPOTENCY_KEY_REQUIRED`（幂等过滤器对 `/api/v1/projects/**` 写方法强制）。
- 同键 + 相同请求体重试会**回放首次 204**（幂等）；同键 + 不同请求体返回 `409 IDEMPOTENCY_KEY_REUSED`。所以**每次新上传用新 UUID**；只有「上次 204 没收到、想重试」时复用同一键。
- 大于 1MB 的文件：幂等哈希只覆盖前 1MB 前缀（两个路径口径已一致），同键同文件重试可安全回放。

### 4.3 把 204 当成功

- 上传成功响应为 **204 无响应体**，不要尝试解析 JSON body，也不要因为「空 body」判失败。
- 收到 204（或幂等回放的 204）后，走 3.3 confirm。

### 4.4 上传失败/重试建议

1. **网络中断 / 超时且未收到 204**：复用同一 `Idempotency-Key` 重发（安全，服务端会回放首次结果或幂等处理）。
2. **收到 4xx**：按 §5 错误码表处理，通常需要重新走 3.1 拿新凭证（凭证可能过期，或状态已非 PENDING）。
3. **收到 5xx**：可直接重试（新键或同键均可），500 现已被收窄为真正的服务异常，不再掩盖路径/方法错误。

## 5. 错误码表（统一信封 `{ "error": { code, message, details }, "requestId" }`）

| HTTP | code | 场景 |
|---|---|---|
| 400 | `IDEMPOTENCY_KEY_REQUIRED` | PUT/confirm 缺少 `Idempotency-Key` |
| 400 | `ATTACHMENT_SIZE_REQUIRED` | `sizeBytes <= 0` |
| 401 | `UNAUTHORIZED` | 无有效认证 Cookie（迁移期旧 Bearer 仍受后端兼容） |
| 403 | `FORBIDDEN` | 非项目成员 |
| 404 | `NOT_FOUND` | **路径不存在**（原 500 的场景，现在正确返回 404） |
| 404 | `ATTACHMENT_NOT_FOUND` | 附件不存在或不属于该项目 |
| 405 | `METHOD_NOT_ALLOWED` | 路径存在但方法不对（如对仅 GET 的路径发 POST） |
| 409 | `ATTACHMENT_NOT_PENDING` | 上传/确认时状态非 PENDING |
| 409 | `ATTACHMENT_NOT_UPLOADED` | confirm 时对象未上传（先 3.2 再 3.3） |
| 409 | `ATTACHMENT_NOT_READY` | 预览/下载访问非 READY 附件 |
| 409 | `IDEMPOTENCY_KEY_REUSED` | 同键不同请求体 |
| 413 | `ATTACHMENT_TOO_LARGE` | 超过大小上限（默认 50MB） |
| 501 | `ATTACHMENT_DOWNLOAD_UNSUPPORTED` | 本地模式下调用 `download-url`（改用 preview/content） |
| 500 | `INTERNAL_ERROR` | 真正的服务端异常（已不再被路径不存在误触发） |

## 6. 双存储模式行为差异

同一套前端代码无需区分模式，后端按 `aliyun.oss.enabled` 决定写入目标：

| 行为 | OSS 模式（默认生产） | 本地模式（`aliyun.oss.enabled=false`） |
|---|---|---|
| 上传写入 | 后端 `oss.putObject` → 桶 `qgents` | 本地磁盘 `./data/attachments/{objectKey}` |
| `uploadUrl` | `/api/v1/projects/{pid}/attachments/{aid}`（相对） | 同左，完全一致 |
| `download-url` | 预签名 GET 地址 | `501 ATTACHMENT_DOWNLOAD_UNSUPPORTED` |
| `preview-url`/`preview`/`content` | 可用 | **可用**（改造后本地可回读字节） |
| confirm 校验 | `doesObjectExist` | 本地文件存在性 |

**如何确认当前是哪种模式**：上传后看 OSS 控制台 `qgents` 桶是否有对象，或后端进程目录下是否生成 `./data/attachments/` 文件。

> 后端不会自动读取 `.env`；`ALIYUN_OSS_ENABLED=true` 需在启动进程时注入环境变量（IDE / `set -a && source .env`）才生效，否则按 `false` 走本地模式。
